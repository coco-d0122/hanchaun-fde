# 瀚川工业园 · 能耗异常定位智能体（第一阶段命令行原型）

> 单文件 Python 原型，用于验证三条核心链路：
> **① 知识库混合检索问答　② 确定性计量异常检测　③ 检测结果 + 知识依据驱动的 AI 辅助分析**
>
> ⚠️ 本项目所有知识文档均为**模拟规则**，所有电表数据均为**模拟数据**，不代表瀚川工业园已确认的真实制度或真实验收指标。

### 1.1 环境要求

| 项 | 要求 |

| 操作系统 | Windows / macOS / Linux 均可 |

### 1.2 安装依赖

```bash
cd prototype
python -m venv .venv

# Windows
.venv\Scripts\activate
# macOS / Linux
source .venv/bin/activate

pip install -r requirements.txt
```

国内网络如果安装缓慢，可加镜像：

```bash
pip install -r requirements.txt -i https://mirrors.aliyun.com/pypi/simple/
```

```bash
# Windows
copy .env.example .env
# macOS / Linux
cp .env.example .env
```

然后编辑 `.env`，最少只需改两项：

```ini
LLM_PROVIDER=deepseek
LLM_API_KEY=sk-你的密钥
```

**没有 API Key 也能跑**：程序会自动降级为"离线模拟模式"，检索、检测、证据、溯源全部照常执行，只有 AI 那段自然语言由模板生成，并会在输出中明确标注 `【离线模拟输出｜未调用真实大模型】`。这是刻意设计——用来区分"链路是否打通"和"模型是否可用"两件事。

想验证语义检索效果，再配 `EMBEDDING_PROVIDER=api`（复用同一套 Key 与地址）。

## 三、测试数据说明

### 3.1 场景一：`meter_readings_normal.csv`（正常）

- 1 栋楼（B1）、5 块表（1 总表 + 4 分表）、96 个 15 分钟点 = 480 条
- 总表按"分表真实电量 × 1.015（模拟线路损耗）"生成，物理自洽
- **预期结果：0 条异常事件**（验证不误报）

### 3.2 场景二：`meter_readings_anomaly.csv`（含注入异常）

- 2 栋楼（B1、B2）、8 块表、96 个点 = 768 条
- **注入异常 1（倍率）**：B1 的 M-002 在第 10 小时起，上报倍率由 `10` 变成 `100`，但表底照常走字
  → 该表电量被放大 10 倍，同时导致 B1 分表合计远大于总表
- **注入异常 2（表计少计）**：B2 的 M-005 从第 12 小时起计量值只有真实的 60%（模拟 CT 二次侧接触不良）
  → 总表大于分表合计，差异率约 +22%
- **预期结果：3 条事件**

| 事件编号 | 规则 | 电表 | 现象 |
|---|---|---|---|
| AN-20261023-0001 | R04 倍率变化 | M-002 | 10 → 100，10 倍变化，级别高 |
| AN-20261023-0002 | R05 总分平衡差 | MT-B1 | −196.0%（分表合计远大于总表） |
| AN-20261023-0003 | R05 总分平衡差 | MT-B2 | +22.0%（总表大于分表合计） |

两条异常**互相印证**是这套数据的价值所在：倍率错 → 该表虚增 10 倍 → 总分差转负。AI 分析报告会把这条因果链讲清楚，这正是"定位"而非"报警"的差别。

### 3.3 数据格式

```csv
meter_id,timestamp,raw_reading,multiplier,unit,building_id,parent_meter_id
MT-B1,2026-10-23 00:00,65141.401339,40,kWh,B1,
M-001,2026-10-23 00:00,21685.937418,10,kWh,B1,MT-B1
```

| 字段 | 说明 |
|---|---|
| meter_id | 电表编号 |
| timestamp | 采集时间（`2026-10-23 10:00` 或 ISO8601） |
| raw_reading | 累计示值（表底），二次侧原始读数 |
| multiplier | 倍率（CT×PT 折算系数） |
| unit | 计量单位，支持 kWh / MWh / Wh |
| building_id | 所属楼栋 |
| parent_meter_id | 上级电表编号，总表留空 |

### 5.3 关键算法说明

**① 切片为什么按段落打包而不是定长切**

定长切会把"倍率变更需填写《计量配置变更单》"切成两半，检索命中后上下文残缺，喂给模型反而制造幻觉。`pack_paragraphs()` 按空行拆段落后逐段塞进 buffer，塞不下就落盘并用上一块末尾 50 字符做前缀，保证跨块语义连续。

**② 为什么索引文本要拼标题**

切片正文里往往不出现"总表""分表"这类主题词（它们只在文档标题里）。`Chunk.index_text()` 把 `文档标题 · 标题路径` 拼到正文前面一起建索引，几乎零成本地显著提升召回。展示与喂模型时仍用纯正文。

**③ RRF 为什么不改成加权分数相加**

向量余弦相似度（0~1）与 BM25 分数（0~几十）量纲完全不同，直接加权必须先归一化，而归一化方式本身又是超参。RRF 只用"排名"这一个信息，天然免疫量纲问题，k=60 是原论文给出的鲁棒默认值。

**④ 区间电量的三个坑**

```python
delta = cur.raw_reading - prev.raw_reading      # 坑1：不能直接累加表底
energy = delta * prev.multiplier * unit_factor  # 坑2：先差分再乘倍率；倍率取"区间起点生效的版本"
if delta < 0: 标记 rollback，不产生电量        # 坑3：表底回退不得参与平衡计算
```

倍率取 `prev.multiplier` 而非 `cur.multiplier`：这段走字是在上一个读数到本读数之间产生的，理应按当时配置换算。若用 `cur`，倍率刚切换的那个区间会被整体放大 10 倍，凭空制造一天的虚假跳变。

**⑤ 数值溯源校验（`number_trace_guard`）**

把所有证据（Python 算出的 metrics + 原始数据快照）与检索片段拼成"允许数值集合"，逐个检查模型回答里的数字是否在里面。找不到来源的数字单独列出并告警。这是防"模型顺手编个看起来合理的数字"最有效的手段。

局限必须承认：它只能发现"数字没有来源"，发现不了"数字有来源但被错误解读"。后者仍依赖人工复核——这正是系统强制所有 AI 结论必须人工签认的原因。

校验前会先剔除日期、时间、引用编号 `[1]`、序数"第2步"，否则 `2026-10-23 10:00` 会被拆成 5 个数字造成大量误报。

**⑥ "依据不足"怎么判（`has_evidence`）**

RRF 是"排名"函数，只要有候选就一定有分数——即使问题与知识库毫无关系，向量那一路也会返回 Top10，RRF 照样能到 0.03。所以**不能用 RRF 分数作为"有没有依据"的判据**，必须回到原始信号：

1. Top1 片段至少命中 **2 个不同**的查询词（只命中 1 个不算——问"今天食堂有什么菜"时，"今天"这个词恰好出现在某条归属说明里，单靠它会得到完全无关的答案）；
2. 或者 Top1 的余弦相似度达到该 Embedding 模式的门槛（hash 模式 0.08，语义模型 0.30）。

实测效果：

| 问题 | 判定 |
|---|---|
| 电表倍率发生变化时应该如何处理？ | 有依据 |
| 总表与分表数据不一致可能有哪些原因？ | 有依据 |
| 如何判断能耗异常是否由计量错误引起？ | 有依据 |
| 发现电表数据异常后需要哪些人工复核步骤？ | 有依据 |
| 能耗异常分析报告应该包含哪些证据？ | 有依据 |
| 今天食堂有什么菜？ | **依据不足** |
| 公司年会什么时候举办？ | **依据不足** |

命中"依据不足"时，程序不会调用大模型编答案，而是直接告知无法回答并建议补充文档。

## 六、已知边界与下一步

### 6.1 本阶段刻意不做的事

| 不做 | 原因 |
|---|---|
| FastAPI / Web 页面 | 本阶段只验证算法链路 |
| 数据库 | 内存 + CSV 足够验证逻辑；表结构已在架构方案中定义 |
| 多智能体框架 | 单 Agent + 受控工具序列已足够，复杂框架会掩盖真实问题 |
| 真实 EMS 对接 | 无现场环境；`adapters/` 层已预留接口形态 |
| 机器学习异常模型 | 240 表规模、无标注数据、且黑箱模型难以产出可复核证据 |

### 6.2 已知局限

1. **hash 模式不是语义检索**。它本质是"词形相似"，同义词（"倍率"与"变比"）不会自动靠近。生产环境必须切 `EMBEDDING_PROVIDER=api` 或 `st`。
2. **R04 只做单表检测**，未结合配置历史表判断"变化是否合法"。正式系统要查 `meter_config_history` 与换表工单。
3. **R05 未做缺数处理**。若某分表整段无数据，会被当作 0 计入求和，从而放大差异。正式系统要先判数据完整性。
4. **倍率变更那一刻的区间归属**是简化处理（见 §5.3 ④），正式系统应按配置生效时间精确切分区间。
5. **阈值是模拟参数**，3% / 1.5× 均未经现场标定。
