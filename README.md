# 瀚川工业园 · 园区能耗监测与异常定位智能体

一套面向工业园区（约 240 块电表 / 15 分钟采集）的能耗异常定位系统的**需求 → 架构 → 原型 → Web 界面 → 管理后台 → 自主 Agent**递进式交付物。

本仓库覆盖项目从立项到阶段 6 的材料：需求澄清、架构设计、已跑通的原型、聊天接口方案、管理后台方案，以及 Agent 工具调用架构。

> ⚠️ **重要声明**
> 本仓库中的业务背景来自**模拟访谈与业务需求发现材料**，部分数据、规则与流程尚未经现场验证。
> 所有知识库文档均为**模拟规则**，所有电表数据均为**模拟数据**，均不代表瀚川工业园已确认的真实管理制度或真实验收指标。
> 代码中出现的阈值（3%、1.5 倍等）仅作测试参数，不构成合同约定的验收口径。

## 二、快速开始

```bash
cd prototype
pip install -r requirements.txt
cp .env.example .env          # Windows: copy .env.example .env
python energy_agent.py --demo # 全链路演示，约 30 秒
```

**没有大模型 API Key 也能跑**：程序自动降级为离线模拟模式，检索、检测、证据、溯源全部照常执行，只有 AI 那段自然语言由模板生成，并在输出中明确标注。

也可以进入交互菜单：

```bash
python energy_agent.py
```

## 三、原型验证了什么

| 能力 | 实现方式 | 实测结果 |
|---|---|---|
| 知识库混合检索问答 | BM25 + FAISS 双路召回，RRF 融合取 Top3 | 5 个业务问题全部命中并标注来源 |
| 拒绝无依据回答 | Top1 须命中 ≥2 个查询词，或余弦相似度达阈值 | "今天食堂有什么菜" → 判定依据不足，不调模型 |
| 确定性计量异常检测 | 规则 A 倍率突变 / 规则 B 总分表平衡差 | 正常数据集 0 误报；异常数据集 3/3 命中 |
| AI 辅助分析 | 异常上下文 + 知识检索 → 提示词 → LLM | 输出含现象/原因/依据/核查建议/是否需复核 |
| 数值溯源校验 | 正文每个数字须能在工具返回值中找到（容差 0.5%） | 不匹配则整篇标记为未通过 |
| 故障降级 | API 超时重试后转模板输出 | 规则结论与证据完整保留，链路不中断 |

两处注入的故障是**互相印证**的：M-002 倍率由 10 误录为 100 → 该表电量虚增 10 倍 → B1 分表合计远超总表（差异率 −196%）。AI 报告能把这条因果链讲出来，这才叫"定位"而不是"报警"。

## 四、几个关键设计取舍

1. **不引入时序数据库**。240 表 × 96 点/日 ≈ 840 万行/年，5 年 < 5 GB。原生 PostgreSQL 按月分区 + 物化视图足够，TimescaleDB 的收益在数据量级不足时无法覆盖其运维成本。
2. **倍率版本重叠用数据库约束兜住**，而非代码判断：`EXCLUDE USING gist (meter_id WITH =, tstzrange(...) WITH &&)`，让"同一块表同一时段两个倍率"在录入时即报错。
3. **AI 不改数靠数据库角色，不靠提示词**：智能体工具层使用只读角色 + 只读事务，对能耗表无 UPDATE/DELETE 权限。
4. **"异常"必须先分类**：数据质量异常 / 计量异常 / 能耗异常 / 归属异常四类的判定方法、责任人、处置动作完全不同。不分类会退化成"什么都报、谁都不信"的报警器。
5. **"依据不足"不能用 RRF 分数判定**。RRF 是排名函数，只要有候选就一定有分数，必须回到原始相似度与词命中上判断。

## 六、技术栈

Python 3.11+ / FAISS / rank-bm25 / jieba / numpy / requests / python-dotenv；大模型走 OpenAI 兼容接口，可切换供应商。

正式架构规划为：FastAPI + PostgreSQL（含 pgvector）+ APScheduler + Vue3，Docker Compose 四容器部署，整体保持单体模块化，不做微服务。
